## <a name="rus"></a> 1. Основные цели

- Уменьшение когнитивной нагрузки.
- Увеличение скорости работы с кодом.
- Предотвращение типичных ошибок.
- Учитывать специфику разработки на Svelte 5.
- НЕ являться всеохватывающим документом. Если вы не видите здесь ответы на какие-то вопросы, попробуйте поискать их в [Google TypeScript Style Guide](https://google.github.io/styleguide/tsguide.html), [TypeScript Handbook](https://www.typescriptlang.org/docs/handbook/intro.html), [Airbnb JavaScript Style Guide](https://github.com/airbnb/javascript).

## 2. Именование

### [↑](#rus) 2.1. Переменные и константы

Главная метаинформация переменных и констант - это вариант их хранения и единицы измерения. По-этому, чтобы облегчить с ними работу, настоятельно рекомендуется придерживаться следующего формата именования:  
`prefix_camelCase_suffix`

Таким образом, название состоит из 3-х частей, **разделённых** символом `"_"`. Левая и правая часть могут отсутствовать в зависимости от контекста.

**Префикс** указывает на вариант хранения, в порядке уменьшения приоритета:
1. Для глобальных: `g_`. Но лучше `g.`, как в примере с `global.svelte.ts`:
   ```ts
   export class Global {
       public on1Hz: boolean = $state(false);
   } // class Global
   export var g: Global = new Global;
   export default g;
   ```
0. Для статических полей классов - не используется, так как синтаксис: `ClassName.field`.
0. Для других полей структур и классов - не используется, так как синтаксис: `this.field`.
0. Для локальных: не используется.
0. Для констант, у которых область видимости:
    - Блочная: без префикса.
    - Локальная: без префикса.
    - Компонентная, модульная, классовая: без префикса для реактивных.
    - Компонентная, модульная, классовая: `c_` для нереактивных.
    - Глобальная: `c.`, по аналогии с `g.`.

Терминология областей видимости (scope):
- Блочная — внутри циклов, условий, шаблонов (Svelte).
- Локальная — для функций.
- Классовая — для полей класса.
- Компонентная — для `<script>` внутри `.svelte` файла.
- Модульная — для неэкспортированных переменных, функций, классов внутри `.ts` файла.
- Глобальная — для экспортированных.

Существуют разные варианты работы с единицами измерения, в порядке уменьшения полезной нагрузки:
1. [Type Driven Development](https://habr.com/en/post/459620/) - целая методология.
2. `duration: time_ms;` - отдельный тип данных, проверки на этапе компиляции.
   <details><summary>Неутешительный пример</summary>

    ```ts
    type TimeMs = `${number}_ms`;
    type SizePx = `${number}_px`;

    const delay_ms: TimeMs = "100_ms"; 
    const width_px: SizePx = "100_px";

    class time_ms {
        constructor(value_ms: number = 0) {
            this.value_ms = value_ms;
        }
        add(other: time_ms | time_us): time_ms | time_us {
            if (other instanceof time_ms) {
                return new time_ms(this.value_ms + other.value_ms);
            }
            return new time_us(this.value_ms * 1000 + other.value_us);
        }
        value_ms: number = 0;
    }
    class time_us {
        constructor(value_us: number = 0) {
            this.value_us = value_us;
        }
        add(other: time_ms | time_us): time_us {
            if (other instanceof time_us) {
                return new time_us(this.value_us + other.value_us);
            }
            return new time_us(this.value_us + other.value_ms * 1000);
        }
        value_us: number = 0;
    }
    ```
   </details>
3. `duration_ms: number;` - суффикс, видно в любом месте работы с переменной.
4. `duration: number; // ms` - комментарий, видно лишь в месте декларации, или если _IDE_ умеет выводить подсказки.
5. `duration: number;` - метаинформация о единицах измерения отсутствует.

Следовательно:
- 1 и 2 - использовать по ситуации.
- 3 - рекомендуется, так как это оптимальный вариант между затратами времени и количеством полезной информации.
- 4 и 5 - не использовать.

Следовательно, **суффикс** указывает на единицы измерения если они применимы. Например: `_ms`.

Некоторые нюансы по единицам измерения:
- Проценты `%` можно сократить как `_prc`.
- _something PER something_ -> _something/something_ -> _something IN something_  
  `m/s -> _mIs -> _m_s`  
  Возможные примеры исключений: `_fps`, `_mph`, так как они привычны.

Некоторые нюансы по названиям переменных:
- `idx` vs `it`. Для переменных-итераторов полезно понимать вариант доступа:  
  `itemIt` (_iterator_), последовательный доступ.
  <details><summary>Пример itemIt</summary>

  ```ts
  import { RedBlackTree } from "data-structure-typed";
  let set = new RedBlackTree<number>();
  const itemIt = set[Symbol.iterator]();
  let item = itemIt.next();
  while (!item.done) {
      const value = item.value;
      console.log(value);
      item = itemIt.next();
  }
  ```
  </details>
  
  `itemIdx` (_index_), смещение от 0, случайный доступ.  
  Возможный пример исключения: `for (... y ...) {  for (... x ...)`.

### [↑](#rus) 2.2. Строковые литералы

Рекомендуется использовать двойные кавычки `"` для строковых литералов в TypeScript коде, и так же для HTML атрибутов. Это обеспечивает консистентность.

### [↑](#rus) 2.3. Типы данных

Рекомендуется: `PascalCase`. В том числе, для элементов перечислений.

Примеры:
```ts
type User = { name: string; age: number };
interface ApiResponse { status: number; data: unknown };
enum ErrorStatus { Success, Failed, Timeout };
```

### [↑](#rus) 2.4. Функции и методы

Рекомендуется: `camelCase_suffix`.  
Для функций, возвращающих значения, которые имеют единицы измерения, можно применить ту же логику суффикса, как для переменных и констант.

Для консистентности, а также для снижения когнитивной нагрузки, рекомендуется явно описывать единицы измерения в суффиксе и для геттеров и для сеттеров.

> При нескольких параметрах функции, проблемы не возникнет, так как для всех параметров применяется та же логика с суффиксами.

### [↑](#rus) 2.5. Пространства имён

Рекомендуется: `snake_case`.

Отдельно можно рассмотреть пример организации утилит в пространствах имён:  
Если в нескольких файлах сделать `export namespace utils`, то, при `import utils` сразу из нескольких файлов, будет дублирование идентификатора `utils`. За счёт того, что утилиты можно назвать чем-то уникальным для проекта, им можно выделить букву `u`, и дополнить её контекстом конкретного файла утилит. Например: `u_a` - работа с массивами, `u_n` - работа с числами, `u_s` - работа со строками, `u_dt` - работа с датой и временем.

## 3. Типы данных

### [↑](#rus) 3.1. Целочисленные типы

Использовать `number` для обычных числовых значений. Для больших целых чисел использовать `bigint`. Помнить о `Number.MAX_SAFE_INTEGER` (2^53 - 1) при работе с большими числами.

При работе с индексами массивов:
```ts
const size = 5;
const idx = size / 2;
const element = array[Math.floor(idx)];
```

## 4. Числовые литералы

Основная логика метаинформации здесь - нижний регистр для специальных разделителей (`0x0 0b0 0.0f 0.0e+0`), верхний регистр для цифр (`0xABCD`). Явное различие разделителей и цифр облегчает восприятие.

Для плавающей точки, всегда пишется целая и дробная часть, например: `0.0`.

## 5. Структура кода

### [↑](#rus) 5.1. Иммутабельность

Стараться везде, где это возможно, явно обозначать иммутабельность используя `const`, `as const`, `readonly`, `Readonly<>`.  
Это добавляет полезную метаинформацию при чтении и работе с кодом, и позволяет компилятору найти больше оптимизаций.

```ts
const c_color = [ "#000000", "#FFFFFF" ] as const;

const c_roles = {
    ADMIN: "admin",
    EDITOR: "editor",
    GUEST: "guest",
} as const;

class Circle {
    readonly radius: number;
}

const c_range: Readonly<Record<number, number>> = {
    1: 4,
    2: 2,
};
```

### [↑](#rus) 5.2. Ширина строк

Нормальная: до 80 символов. Рекомендованная: до 100 символов.

Другими словами, стремиться помещаться в 80 символов, но можно превышать до 100 символов, и можно превышать больше 100 если это однотипный декларативный код (например, инициализация сложного массива через `{}` в виде таблицы, или огромный тэг `<svg>`).

> Компактный по горизонтали код значительно быстрее читать.

### [↑](#rus) 5.3. Комментарии

Однострочные `//` для постоянных комментариев, многострочные `/**/` для быстрого временного отключения участков кода. Комментарии `/**/` не должны попадать в репозиторий, чтобы в будущем, при быстром отключении участков кода, между `/**/` не оказалось ещё одних `/**/`. Плюс, комментарии вида `//`, легко читаются без подсветки синтаксиса.

Если функция имеет неочевидную алгоритмическую сложность, и если, тем более, предполагается её множественный вызов, то полезно обозначить её алгоритмическую сложность в комментарии.  
Примеры для вычислительной сложности:
```ts
// Omin(n)       или Ω(n)       или O_(n)
// Oavg(n log n) или O̅(n log n) или O~(n log n)
// Omax(n^2)     или O(n^2)     или O^(n^2)
// Oeq(1)        или Θ(1)       или O=(1)
```
Для сложности по памяти, например, можно добавить "M": `OMavg(...)`.

Код реактивных обработчиков (внутри `$state`, `$derived`, `$derived.by`, etc), помимо основной логики, содержит логику реактивности, которую не видно явно. Это увеличивает когнитивную нагрузку при анализе такого кода. Чтобы её снизить, рекомендуется в начале каждого такого обработчика описывать применённые к реактивным переменным операции:
```ts
$state(() => {
    // one: read
    // two: write
    // three: read & untracked write
    // four: untracked read & write
    // five: untracked read & untracked write
    // six: read & conditional write

    ... code
});
```
> Соответственно, `read & write` запрещено, поскольку создаёт рекурсию.

Иногда, возникают случаи ожидаемых ошибок, которые не ломают сборку или работу проекта, но при этом назойливо подсвечиваются линтером. Чтобы такое решить, можно локально отключить проверку, используя специальный комментарий:
```ts
//@ts-expect-error
```

### [↑](#rus) 5.4. Отступы и скобки

Для отступов использовать 4 пробела, так как 2 слишком мало для императивного кода, а 8 слишком много. Табуляция создаёт известные проблемы.
> 2 пробела могут подойти для декларативного кода на другом языке, когда логических ветвлений меньше либо отсутствуют, и когда вложенности больше.

Открывающие скобки (`{`, `<`, `(`, `[`) НЕ располагать на отдельной строке для всех языковых конструкций. Далее будут приведены разные примеры.
> Компактный по вертикали код значительно быстрее читать.

Для параметров не влезших в первую строку, добавляется дополнительный отступ, чтобы не сливалось с телом:
```ts
function foobar(aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa: number,
        bbbbbbbbbbbbbbbb: number, cccccccccccccccccccccccccc: number,
        dddddddddddddddddddddddddddddddddddddddddd: number): void {
    body();
}
```

Длинные подвыражения лучше читаются на отдельных строках, при этом, операторы лучше читаются в начале строк:
```ts
if ((conditionA && conditionB)
        || (conditionC && conditionD)
        || (conditionE && conditionF)) {
    ...
}
```

Количество закрывающих скобок в одной строке должно быть равно количеству открывающих на этом же уровне отступа:
```ts
action(process(  // +2
    argumentA, argumentB, argumentC,
    calculate(  // +1
        argumentD, argumentE
    )  // -1
));  // -2
```
Исключение: если код простой, можно закрывать круглую скобку в конце строки с кодом, чтобы не раздувать код по вертикали.

Комплексный пример:
```ts
export namespace some {

export class Foo extends Bar implements Baz {
    private a: number;
    private b: number;
    private c: number;
    private d: number;

    constructor(a: number, b: number, c: number, d: number) {
        this.a = a;
        this.b = b;
        this.c = c;
        this.d = d;
    }

    getObject(): Object | null {
        return condition
            ? s_someDefault
            : condition
                ? this.someExist
                : null;
    }
    setObject(object: Object | null): void {
        this.someExist = object;
    }

    // Название функций-слотов должно начинаться на "on"
    onSome(): void {
        if (conditionA) {
            ...
        }
        else if (conditionB) {
            ...
        }
        else {
            ...
        }

        switch (variable) {
        case variantA:
            if (condition) {
                break;
            }
            break;
        case variantB: {
            break;
        }
        default:
            break;
        }
    }

    onProcess10Hz(): void { // Если период вызова фиксированный, пишите его в названии
        ...
    }
} // class Foo

} // namespace some
```

### [↑](#rus) 5.5. Пустые разделяющие строки

Группировка связанных строк кода написанием их слитно, и разделение менее связанных пустыми строками - значительно облегчает чтение и работу с кодом. Другими словами, можно легко увидеть более связанные строки, не вынося их в отдельные функции, или не добавляя очевидные разделяющие комментарии. Обдуманная связанность разных строк даёт полезную контекстную информацию.

Между секциями JS/TS, HTML, CSS рекомендуется ставить две пустые строки, чтобы визуально разделить принципиально разные части кода.

### [↑](#rus) 5.6. Логические проверки

При чтении и понимании работы кода логических проверок, полезно видеть метаинформацию о типе сравниваемых элементов. Для этого, вводится разделение на три группы:
```ts
if (boolean)                 if (!boolean)
if (number !== 0)            if (number === 0)
if (pointer !== null)        if (pointer === null)
```

Если значения можно расположить в одной системе координат, то их проверки следует размещать по порядку горизонтальной оси:
```ts
// good
if (button.x_px <= mouse.x_px && mouse.x_px <= button.x_px + button.w_px)

// bad
if (mouse.x_px >= button.x_px && button.x_px + button.w_px >= mouse.x_px)
```
Из этого следует, что, для таких значений, не рекомендуется использовать операторы `>` и `>=`, так как координаты растут слева направо.

### [↑](#rus) 5.8. Передача объектов

Передача через ссылку:
```ts

```

Передача через копию:
```ts

someFunc({ ...someObject });
someFunc(Object.assign({}, someObject));

// Глубокое копирование
const deepCopy = structuredClone(someObject); // Начиная с 2022 года
// Не рекомендуется, так как ломает типы данных (Map, Set, Date, регулярные

```

### [↑](#rus) 5.9. Перечисления (WIP)

TypeScript предоставляет возможность сделать перечисления (enumeration) разными способами,
с разными возможностями и стоимостью.

| **Вариант** | **runtime-объект** | **Стрингификация значения** | **Значение и ключ по индексу** | **Ключ по значению** | **Значение по ключу** | **В компонентах** | **Когда выбирать** |
| :- | :- | :- | :- | :- | :- | :- | :- |
| `type EnumOfLiterals = "A" \| "B"` | Отсутствует | Если строковые литералы | Нет | Нет | Нет | Да | Современный универсальный стандарт для TS. Нужна только проверка типов, без JS-кода |
| `const enum ConstEnum { A, B }` | Отсутствует при инлайнинге | Если строковые литералы | Нет | Нет | Да | `tsc`: да<br> `esbuild`: проблемы | Нужен инлайнинг значений в JS для критичной производительности и защиты кода. Но, при `isolatedModules`, требует специальной сборки |
| `const ObjectAsEnum = { A: "A" } as const` | Минимальный | Если строковые значения | Вручную | Вручную | Да | Да | Рекомендуемая альтернатива для `EnumOfLiterals`, если нужна работа с ключами и значениями, при безопасном tree-shaking с JS-объектом |
| `const ArrayAsEnum = [ "A", "B" ] as const` | Минимальный | Если строковые значения | Да | Вручную | По индексу | Да | Рекомендуемая альтернатива для `EnumOfLiterals`. Идеально, когда порядок элементов важен, и нужна лёгкая итерация (`Array.map/includes`) |
| `enum StringEnum { A = "A" }` | До TS 5.0 - IIFE, после - объект, хуже tree-shaking | Да | Нет | Вручную | Да | Если настроить | Требуется строгая номинативная типизация (Nominal Typing) и наглядные значения в логах/API |
| `enum NumericEnum { A, B }` | До TS 5.0 - IIFE, после - объект, reverse mapping, хуже tree-shaking | Нет | Да | Да | Да | Если настроить | Нужна двунаправленная связь (ключ <=> индекс) или битовые флаги |
| `class ClassAsEnum { static readonly A = "A"; }` | Минимальный | Если строковые значения | Вручную | Вручную | Да | Да | Паттерн Smart Enum / Rich Enum, когда у значения enum должны быть методы. Не рекомендуется, так как подмешивать методы можно ко всем runtime-вариантам |

> "В компонентах" :: "Если настроить" - `vitePreprocess({ script: true })`

Для передачи `ObjectAsEnum`, `ArrayAsEnum`, `ClassAsEnum` в функции, им нужно определить тип:
```ts
const ObjectAsEnum = { Small: "S", Large: "L" } as const;
type ObjectAsEnum = typeof ObjectAsEnum[keyof typeof ObjectAsEnum];
```

Пример продвинутого использования `ArrayAsEnum`:
```ts
export const c_errorCodes = [
    "NETWORK_FAILURE",
    "INVALID_INPUT",
    "TIMEOUT",
] as const;
export type ErrorCode = typeof c_errorCodes[number];

const c_errorCodesSet: ReadonlySet<string> = new Set(c_errorCodes);
export function isErrorCode(value: string): value is ErrorCode { // предикат
    return c_errorCodesSet.has(value); // O(1) проверка
}

// compile-time проверка соответствия c_errorCodes
export const c_errorText: Readonly<Record<ErrorCode, string>> = {
    NETWORK_FAILURE: "Сбой сети",
    INVALID_INPUT:   "Неверные данные",
    TIMEOUT:         "Таймаут",
};
```

Не рекомендуется использовать смешанный `enum` (числа и строки в значениях), так как это создаёт неоднозначность при сериализации и итерации.

### [↑](#rus) 5.10. Функции

Рекомендуется явно указывать типы параметров и возвращаемых значений:

```ts
function calculateSum(a: number, b: number): number {
    return a + b;
}

// Для асинхронных функций
async function fetchData(url: string): Promise<Data> {
    const response = await fetch(url);
    return response.json();
}

// Для функций с опциональными параметрами
function processItem(item: Item, options?: ProcessOptions): void {
    // ...
}
```

Выбор между объявлением через `function` и лямбдой (стрелочной функцией), делается по **первому подходящему** условию из списка:
```ts
// 1. Если метод класса - function
class Session {
    // good
    update(state: State): void { ... }
    // bad
    update = (state: State): void => { ... }
}

// 2. Если нужна перегрузка функций - function
function parse(value: string): number;
function parse(value: string[]): number[];
function parse(value: string | string[]): number | number[] {
    ...
}

// 3. Если существует в контексте аргументов - lambda
const activeItems = items.filter((item) => item.isActive);
setTimeout(() => this.close(), c_closeDelay_ms);
onMount(() => {
    // good, одинаковый объект, удаление работает
    const onClick = (event: MouseEvent) => onClickPage(event);
    document.addEventListener("click", onClick);
    return () => document.removeEventListener("click", onClick);
 
    // bad, разные объекты, подписка не удаляется, утечка памяти и баги
    document.addEventListener("click", (event) => onClickPage(event));
    return () => document.removeEventListener("click", (event) => onClickPage(event));
});

// good
function onClickPage(event: MouseEvent): void {
    ...
}
onMount(() => {
    document.addEventListener("click", onClickPage);
    return () => document.removeEventListener("click", onClickPage);
});


// 4. Если занимает одну строку, не имеет ветвлений (if, switch, тернарный оператор)
// и не содержит побочных эффектов (изменение внешнего состояния, вызов функций,
// меняющих состояние) - lambda
const toPercent = (ratio: number): number => ratio * 100;

// 5. Если захватывает изменяемое состояние (с мутацией внешних переменных),
// или содержит сложную логику с состоянием - function
// good
function accumulate(values: number[]): number {
    let total = 0;
    for (const value of values) {
        total += value;
    }
    return total;
}
// bad
let total = $state(0);
const accumulate = (value: number): void => { total += value; };

// 6. Иначе - function
```

### [](#rus) 5.11. Точка с запятой

В конце строк, `;` следует ставить почти всегда, чтобы не случилось подобного:
```ts
const str = "string"
[1, 2, 3].forEach( ... ) // Ошибка: Попытка индексации по "string"

let idx = c_default
(function() { ... })() // Ошибка: Попытка вызова c_default

let idx = c_default
`string` // Ошибка: Попытка вызова c_default
```
Отдельный пример неожиданности:
```ts
return
{
    status: "ok"
}
// return undefined; { status: "ok"; }
```

## 6. Общие принципы программирования

### [↑](#rus) 6.1. _DRY - Don't Repeat Yourself_

Одно из самых весомых и известных правил - **"не повторяйте себя"**. В интернете много написано про это правило, по этому, оно здесь не будет поясняться. Но его можно прокомментировать так, что это базовое правило качественного кода, и много других правил так или иначе связаны с ним.

### [↑](#rus) 6.2. Вложенность

Одно из самых весомых правил - стараться везде использовать ***Return Early Pattern***. Большое количество уровней вложенности заставляет **держать в уме** контексты каждого уровня. Тогда как, при использовании данного паттерна, можно работать со следующими контекстами, зная что предыдущие **обработаны** выше по коду. Также, это способствует лучшей оптимизации, так как одна из стратегий обработки ветвлений в процессоре - выполнение наперёд **самой длинной** ветки кода, которая, в случае применения данного паттерна, содержит **полезный** код, тогда как множество маленьких веток содержат редко выполняемый код.
```ts
function updateState(newState: State): boolean {
    if (!device.isReady()) {
        return false;
    }
    if (prevState == newState) {
        return false;
    }
    switch (newState) {
    case State.Undefined:
    default:
        return false;
    case ...:
        ...
    }
    console.info(`state changed: ${prevState} -> ${newState}`);
    prevState = newState;
    return true;
}
```

### [↑](#rus) 6.3. Комбинаторика

Одно из многих правил, которое следует из правила DRY:  
При написании кода содержащего много вариантов, предпочитайте `O(m + n)` вместо `O(m * n)`:

```ts
// O(m + n), 7 variants, good
switch (message_part0) {
case aa: message += "aa"; break;
case bb: message += "bb"; break;
}
switch (message_part1) {
case cc: message += "cc"; break;
case dd: message += "dd"; break;
}
switch (message_part2) {
case ee: message += "ee"; break;
case ff: message += "ff"; break;
case gg: message += "gg"; break;
}
```

```ts
// O(m * n), 12 variants, bad
switch (message_code) {
case aa_cc_ee: message = "aa_cc_ee"; break;
case aa_cc_ff: message = "aa_cc_ff"; break;
case aa_cc_gg: message = "aa_cc_gg"; break;
case aa_dd_ee: message = "aa_dd_ee"; break;
case aa_dd_ff: message = "aa_dd_ff"; break;
case aa_dd_gg: message = "aa_dd_gg"; break;
case bb_cc_ee: message = "bb_cc_ee"; break;
case bb_cc_ff: message = "bb_cc_ff"; break;
case bb_cc_gg: message = "bb_cc_gg"; break;
case bb_dd_ee: message = "bb_dd_ee"; break;
case bb_dd_ff: message = "bb_dd_ff"; break;
case bb_dd_gg: message = "bb_dd_gg"; break;
}

```

Яркий пример - токены в ресурсах локализации. Каждая строка в интерфейсе может иметь свой токен, и тогда ресурсы сильно растут в размере. Лучше, когда частые названия и фразы выделяются в отдельные токены для частого переиспользования.

### [↑](#rus) 6.4. Обработка ошибок

Хорошая программа не та, которая завершается при любой ошибке, а та, которая старается **продолжать работать не смотря на некритические ошибки**.  
В общем случае, это означает, что нужно игнорировать невалидные данные и ресурсы, иметь запасные варианты при отсутствии необходимых ресурсов, иметь запасные варианты работающего поведения при возникновении логических ошибок. При этом, лучше **избегать использование исключений**, так как они потенциально прервут бОльшую часть цепочки вызовов. Вместо них, лучше на каждом уровне цепочки вызовов делать проверки на успех выполнения вызовов, логируя ошибки в значимых местах, и задействуя запасные обходные варианты, где это необходимо.

### [↑](#rus) 6.5. Оптимизация SVG

Вставляя SVG-ресурсы в исходный код, можно легко не заметить разрастания размера страниц, если эти SVG-ресурсы не оптимизированы с точки зрения векторной графики. Чтобы этого не происходило, рекомендуется пользоваться оптимизаторами SVG, и помечать вставленные неоптимизированные SVG-ресурсы комментариями типа TODO.

Рекомендуемые оптимизаторы:
- [SVGOMG](https://jakearchibald.github.io/svgomg/) — официальный веб-интерфейс для движка SVGO, созданный для интерактивной оптимизации векторной графики. Позволяет визуально настраивать параметры сжатия (округление координат путей, удаление скрытых слоев, лишних групп <g> и редакторских метаданных) с наглядной оценкой результата.
- [SVGO](https://svgo.dev/) — консольная утилита и библиотека на базе Node.js, индустриальный стандарт. Глубоко очищает векторные файлы от "мусора", оставленного графическими редакторами (Figma, Illustrator, Inkscape), удаляет неиспользуемые атрибуты и комментарии, минифицирует SVG-разметку, и оптимизирует массивы координат (d="..."), уменьшая размер файлов без потери визуального качества.
- [SVGM](https://svgm.dev/) — сверхбыстрый инструмент на языке Rust (по некоторым данным, в 33 раза быстрее SVGO). Использует алгоритмический подход "сходимости в фиксированной точке" (fixed-point convergence), циклично применяя оптимизации до тех пор, пока структура SVG не станет максимально компактной, что позволяет достигать рекордной степени сжатия, при мгновенной обработке.

Для компактности, переиспользования, и масштабируемости кода, следует выносить SVG-ресурсы в отдельные файлы. Дополнительно, это позволяет удобно добавлять пропсы к таким ресурсам. Например:
```html
<script lang="ts">
	let {
        level = 1,
        width = "1.5vh",
        height = "1.5vh"
    } : {
        level: number,
        width: string,
        height: string
    } = $props();

	const bars = [
		"M0 22.5h4.3V18H0z",
		"M6.4 22.5h4.3v-9H6.4z",
		"M12.9 22.5H17V9H13z",
		"M19.3 22.5h4.3v-18h-4.3z",
		"M25.7 22.5H30V0h-4.3z"
	] as const;

	const activeColor = "#0F0";
	const inactiveColor = "#1A1A1A";
</script>

<svg width={width} height={height} fill="none"
	    viewBox="0 0 30 23" xmlns="http://www.w3.org/2000/svg">
	{#each bars as pathData, index}
		<path d={pathData} fill={index < level
            ? activeColor : inactiveColor} />
	{/each}
</svg>
```

### [↑](#rus) 6.6. Работа с цепочками распространения данных

Любую программную систему, по возможности, следует представлять как **набор цепочек распространения данных**, от одного конца к другому. Цепочки могут быть как явно направленные, так и зеркальные. Пример направленной цепочки: измерительный датчик можно назвать низом цепочки, а графический интерфейс пользователя - верхом. Пример зеркальной цепочки: передача пакетов в одноранговой сети, при которой, сеть можно называть верхом или центром цепочки.

#### 6.6.1. Разработка в глубину или в ширину

Когда система большая, имеет смысл сначала добиться работающего MVP/proof-of-concept/alpha-version, путём минимальной реализации всей глубины цепочки, без избыточности. Это позволяет раньше оценить жизнеспособность решения, раньше стабилизировать API, раньше проверить гипотезы, раньше начать тестировать другие компоненты системы, раньше распараллелить разработку системы. И далее, для полного покрытия задачи, можно переходить к разработке "в ширину", при которой добавляются все необходимые функции и разнообразие параметров.

> При разработке "в глубину", не стоит забывать про расширяемость архитектуры.

#### 6.6.2. Разработка снизу-вверх или сверху-вниз

Обычно, в начале разработки, один конец цепочки понятен лучше чем другой, что позволяет лучше выставить приоритеты, и выполнять разработку от более понятного конца цепочки, или сразу с двух концов. Примеры разработки "сверху-вниз": начало от протоколов коммуникации между микросервисами, начало от дизайна графического интерфейса. Примеры разработки "снизу-вверх": начало от реализации драйверов, начало от изобретения алгоритмов.

#### 6.6.3. Разработка через тестирование

Как частный случай разработки "сверху-вниз", хорошей практикой является сначала писать модульные тесты, создавая при этом интерфейсы, а затем писать и проверять реализацию этих интерфейсов, сразу получая значительный объём проверенного кода.

#### 6.6.4. Итеративная разработка

Когда система большая, бывает что разработка в полную глубину или полную ширину может потребовать слишком много ресурсов, тогда полезно разделить разработку на крупные этапы, с получением работоспособного продукта на каждом этапе. Иногда это означает, что часть продукта будет временно использовать упрощённые или неоптимальные компоненты, или временно содержать ограниченный набор крупных функций.

#### 6.6.5. Принцип локализации проблемы

Для поиска источника проблемы, следует проверять разные места цепочки, стремясь локализировать проблему. Таким образом, с одной стороны цепочки будет увеличиваться объём корректно работающей логики, а с другой стороны будет увеличиваться объём логики где ошибка прослеживается, пока оно не сойдётся на причинном месте.

### [↑](#rus) 6.7. Оптимизация компиляции

Старайтесь использовать техники ускорения компиляции и сборки, в порядке уменьшения приоритета:
1. TypeScript strict mode
2. ES2022+ target
3. Code splitting (chunks)
4. Tree-shaking
5. SVG optimization
6. Bundle analysis (rollup-plugin-visualizer)

Также, полезно избегать рекурсивных типов в TypeScript, которые могут замедлить компиляцию.

### [↑](#rus) 6.8. Использование нейросетей для работы с кодом

Главная проблема нейросетевого кода — он может быть корректный, но при этом имеет проблемы с метаинформацией и самодокументированием. С ним труднее работать, чем с кодом, написанным осмысленно. И вторая проблема — если не осмысливать такой код, то в проекте появляется отдельный автор — нейронка, и появляется код, который никто не знает, что вырастает в технический долг. Но и пользы нейросети могут приносить много.

Из этого, можно сформулировать две категории использования нейросетей:
- Нейрокодинг: строгое осмысленное точечное использование, самодокументированный масштабируемый код, белая коробка.
- Вайбкодинг: спеки-промпты, без погружения в детали реализации, чёрно-серая коробка.
